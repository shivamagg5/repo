# Database Migration Architecture & Authority Strategy
**Document Version:** 1.0.0 (P0 Remediation Stage)  
**Status:** Authoritative Specification  

---

## 1. Executive Problem Statement (Audit Finding FIX-009)

The platform previously suffered from dual migration authorities:
1. `database/migrations/` (7 legacy SQL files): Contains Postgres extension declarations, RLS policies, and database triggers.
2. `backend/api/src/database/migrations/` (Drizzle kit directory): Contains the active 57-table Drizzle migration snapshot (`0000_light_bushwacker.sql`) and temporary batch files.

Because Drizzle configuration points to `backend/api/src/database/migrations`, running Drizzle migrations did not execute the root SQL files, creating ambiguity about what a fresh vs deployed database represents.

---

## 2. Definitive Unified Architecture

### Single Source of Truth for Schema & DDL
- **Drizzle Schema (`backend/api/src/database/schema/index.ts`)** is the **sole authoritative declaration** of all 57 tables, column types, primary keys, foreign key relations, constraints, and enums.
- **Drizzle Kit (`backend/api/drizzle.config.ts`)** is the **sole migration generator and runner**.

### Extension & Security Policy Layer (RLS & Triggers)
- Row Level Security (RLS) policies, PostgreSQL full-text search indexes (`citext`, `tsvector`), and audit triggers that cannot be declared natively in TypeScript Drizzle schema are maintained as **idempotent SQL scripts** in `database/sql/security_policies.sql`.
- These are executed as a post-migration phase in CI and deployment pipelines.

---

## 3. Two-Tier Migration Execution Plan

### A. Fresh Database Initialization (Staging, Local Dev, CI)
```text
Step 1: PostgreSQL Container / Database created
Step 2: pnpm --filter @platform/api drizzle-kit migrate
        -> Executes 0000_light_bushwacker.sql (Creates all 57 tables & enums)
Step 3: pnpm --filter @platform/api db:apply-policies (or psql -f database/sql/security_policies.sql)
        -> Applies RLS policies, audit triggers, and extension setup idempotently
Step 4: pnpm --filter @platform/api db:seed
        -> Seeds dev/test accounts and taxonomy
```

### B. Existing Deployed Database (Staging / Production Forward Evolution)
```text
Rule 1: NEVER delete or truncate historical migration files.
Rule 2: Schema changes MUST be made in backend/api/src/database/schema/index.ts.
Rule 3: Run `pnpm --filter @platform/api drizzle-kit generate` to generate the next forward migration (e.g. 0001_xxx.sql).
Rule 4: Test forward migration against staging clone before production execution.
Rule 5: Run `pnpm --filter @platform/api drizzle-kit migrate` in pre-deploy job.
```

---

## 4. Preservation & Archival Policy

- **No historical migration files are deleted.**
- Root `database/migrations/` files (0001 to 0007) are preserved for historical audit trails and reference.
- All future migrations are strictly sequential, generated by Drizzle Kit in `backend/api/src/database/migrations/` and committed to git.
